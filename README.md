# 🛡️ VPN Config Collector

جمع‌آوری خودکار کانفیگ‌های VLESS از منابع عمومی و عبور دادن‌شان از یک
pipeline هفت‌لایه. تفاوت اصلی با پروژه‌های مشابه: علاوه بر «سالم بودن سرور»،
**قابل استفاده بودن از داخل ایران** هم تست می‌شود.

## چرا لایه‌ی ایران؟

همه‌ی تست‌های محلی (TCP، TLS، xray) روی رانر گیت‌هاب در آمریکا اجرا می‌شوند.
اندازه‌گیری روی ۳۰ endpoint از خروجی تأییدشده‌ی همین پروژه:

| نقطه‌ی تست | زنده |
|-----------|------|
| نودهای آلمان / آمریکا / هلند | ۳۰ از ۳۰ |
| نودهای ایران (تهران، شیراز) | ۱ از ۳۰ |

یعنی pipeline «سرور سالم» را درست تشخیص می‌داد و «قابل استفاده برای مخاطب»
را نه — همان چیزی که در تست دستی هم دیده شد: از ۲۴۸ کانفیگ خروجی، ۸۸ تا TCP
فعال داشتند و در عمل ۴۴ تا کار می‌کردند. لایه ۳ و لایه ۴ برای بستن همین شکاف
اضافه شدند.

## لایه‌ها

| لایه | کار | نکته |
|------|-----|------|
| ۱ فرمت | پارس VLESS، رد کردن UUID و پورت خراب | `security=none` فقط با ترنسپورت CDN‌پسند قبول می‌شود |
| ۲ حذف تکراری | کلید = uuid + host + port + پارامترها | نام کانفیگ در کلید نیست |
| ۳ TCP | اتصال واقعی، چند تلاش، روی endpoint یکتا | فیلتر سخت: یک تلاش ناموفق = رد |
| ۴ ایران | check-host.net از نودهای ir1، ir3، ir5 | fail-open اگر خودِ API بخوابد |
| ۵ TLS | handshake کامل با SNI درست | Reality هم پوشش داده می‌شود |
| ۶ Geo | کشور از IP، رد کردن کشورهای بلاک | برچسب کشور روی نام کانفیگ |
| ۷ HTTP | ترافیک واقعی از داخل xray، چند دور | سخت‌ترین لایه، فقط با باینری xray |

دو تصمیم که بیشترین اثر را داشتند:

- **تست روی endpoint یکتا، نه روی هر کانفیگ.** در یک پول واقعی ۳۵۱۱ کانفیگ
  فقط ۲۴۶۶ endpoint یکتا داشت؛ سه کانفیگ روی یک `host:port` یک تست می‌گیرند.
- **استثنای CDN بدون TLS.** `security=none` روی IP کلودفلر با ترنسپورت
  ws/httpupgrade/xhttp/grpc اندازه‌گیری‌شده ۲۳ از ۲۴ از ایران جواب می‌دهد،
  در حالی که IP خام VPS حدود ۱ از ۳۰. این دسته عمداً قبول می‌شود.

## خروجی‌ها

| فایل | محتوا |
|------|-------|
| `configs/valid.txt` | هرچه از هفت لایه رد شد، مرتب بر اساس تأخیر |
| `configs/iran.txt` | زیرمجموعه‌ای که از نودهای ایرانی هم جواب داد |
| `configs/top10.txt` | ۱۰ کانفیگ برتر؛ تأییدشده‌های ایران اول |
| `configs/sub_base64.txt` | نسخه‌ی Base64 برای کلاینت‌های قدیمی‌تر |
| `configs/iran_base64.txt` | همان، برای `iran.txt` |
| `configs/countries/XX.txt` | تفکیک کشوری |
| `configs/index.json` | قرارداد ماشین‌خوان: مسیر فایل‌ها + شمارش‌ها |
| `configs/health.json` | اینکه *چرا* یک اجرا خالی یا کم بود |
| `configs/stats.json` | آمار کامل هر لایه |
| `configs/all.txt` | خام، قبل از فیلتر |

قاعده‌ی ثابت این لایه: **هیچ فایلی با محتوای خالی نوشته نمی‌شود.** یک اجرای
ناموفق نباید لینک subscription کاربران را خالی کند؛ خروجی قبلی سر جایش
می‌ماند و دلیلش در `health.json` ثبت می‌شود.

## برچسب روی نام کانفیگ

```
#MyNode|NL|84ms|IR180
```

کشور، تأخیر، و تأخیر اندازه‌گیری‌شده از ایران. نبودن `IR` یعنی لایه ۴ آن را
تأیید نکرده. این اطلاعات روی خودِ لینک است تا ربات و کانال به فایل دوم
وابسته نباشند.

## دو پروسه‌ی مستقل

| پروسه | کجا | کار |
|-------|-----|-----|
| collector | GitHub Actions، هر ۳۰ دقیقه | ساختن پول کانفیگ و commit در `configs/` |
| bot | Railway، همیشه روشن | پاسخ به کاربر + انتشار هر ۵ دقیقه در کانال |

انتشار در کانال عمداً فقط کار ربات است. اگر هر دو پست کنند، دو حافظه‌ی چرخش
مستقل دارند و کانفیگ تکراری داخل بازه‌ی cooldown پست می‌شود. اگر ربات
همیشه‌روشن نداری `PUBLISH_AFTER_COLLECT=1` را ست کن تا هر اجرای collector هم
یک دسته منتشر کند.

هر دوره‌ی انتشار = ۱۰ پیام جدا (هر کانفیگ با مشخصاتش) + یک پیام یازدهم با
لینک subscription. `PUBLISH_COOLDOWN` جلوی تکرار همان کانفیگ‌ها را می‌گیرد تا
کل پول به‌تدریج دیده شود.

## اجرای محلی

```bash
pip install -r requirements.txt
SKIP_TELEGRAM=true SKIP_XRAY=true python -m src.main
```

برای لایه ۷ باینری xray لازم است؛ مسیرش با `XRAY_BINARY_PATH` تنظیم می‌شود.
با `SKIP_CHECKHOST=true` لایه ۴ رد می‌شود (بدون شبکه‌ی خارجی).

## تنظیمات مهم

| متغیر | پیش‌فرض | کار |
|-------|---------|-----|
| `TCP_ATTEMPTS` | 2 | چند اتصال موفق برای قبولی در لایه ۳ |
| `CHECKHOST_MIN_NODES` | 1 | چند نود ایرانی باید جواب دهند |
| `CHECKHOST_TARGET_ALIVE` | 150 | به این تعداد زنده رسید، بس است |
| `CHECKHOST_MAX_ENDPOINTS` | 600 | سقف مصرف سهمیه‌ی API در هر اجرا |
| `HTTP_TEST_ROUNDS` | 3 | چند دور تست HTTP در لایه ۷ |
| `PUBLISH_COUNT` | 10 | چند کانفیگ در هر دوره‌ی انتشار |
| `PUBLISH_INTERVAL_MIN` | 5 | فاصله‌ی دوره‌ها (دقیقه) |
| `PUBLISH_COOLDOWN` | 6 | چند دوره یک کانفیگ تکرار نشود |
| `PUBLISH_AFTER_COLLECT` | false | collector هم پست کند؟ |
